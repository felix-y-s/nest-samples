## 상태 복원(State Reconstruction)이란?

### 핵심 개념

**"상태 복원"**은 이벤트 소싱에서 현재 상태를 얻는 방법입니다.

전통적 DB와의 근본적 차이:

```
전통적 DB: 현재 상태를 DB에 저장
┌─────────────────┐
│ orders 테이블   │
│ id | status     │
│ 123| COMPLETED  │
└─────────────────┘
→ SELECT status FROM orders WHERE id = 123
→ 상태를 "조회"한다 (Read)

이벤트 소싱: 이벤트만 저장, 상태는 필요할 때마다 만듦
┌─────────────────┐
│ event_store     │
│ [Event1]        │
│ [Event2]        │
│ [Event3]        │
│ [Event4]        │
└─────────────────┘
→ 빈 Aggregate 생성 → 이벤트 재생 → 상태 복원
→ 상태를 "복원"한다 (Restore/Reconstruct)
```

### 왜 "복원"이라고 부르나?

- **전통적 DB**: 상태가 이미 존재 → "조회"
- **이벤트 소싱**: 상태가 존재하지 않음 → 이벤트로 **"복원"**

### 코드로 보는 상태 복원

```typescript
// event-store.service.ts
async getOrderById(orderId: string) {
  // 1️⃣ 이벤트 배열 조회
  const events = this.getEventsByOrderId(orderId);
  // events = [
  //   OrderCreatedEvent,
  //   PaymentAttemptedEvent,
  //   PaymentSucceededEvent,
  //   OrderCompletedEvent
  // ]

  // 2️⃣ 빈 Aggregate 생성 (초기 상태)
  const order = new OrderAggregate(orderId);
  // 이 시점:
  //   order.status = undefined ❌
  //   order.finalAmount = 0 ❌

  // 3️⃣ 이벤트 순차 재생 → 상태 "복원"
  for (const event of events) {
    this.applyEventToAggregate(order, event);
  }
  // 재생 완료 후:
  //   order.status = 'COMPLETED' ✅
  //   order.finalAmount = 900000 ✅

  return order; // 복원된 Aggregate 반환
}
```

### 이벤트별 상태 변화

```typescript
// 초기 상태
const order = new OrderAggregate('ORDER-123');
// { status: undefined, finalAmount: 0, userId: undefined }

// Event 1: OrderCreatedEvent 재생
order.onOrderCreatedEvent(event1);
// { status: 'CREATED', finalAmount: 900000, userId: 'USER-001' }

// Event 2: PaymentAttemptedEvent 재생
order.onPaymentAttemptedEvent(event2);
// { status: 'PAYMENT_PENDING', finalAmount: 900000, userId: 'USER-001' }

// Event 3: PaymentSucceededEvent 재생
order.onPaymentSucceededEvent(event3);
// { status: 'PAYMENT_SUCCEEDED', finalAmount: 900000, userId: 'USER-001' }

// Event 4: OrderCompletedEvent 재생
order.onOrderCompletedEvent(event4);
// { status: 'COMPLETED', finalAmount: 900000, userId: 'USER-001' }

// ✅ 최종 상태 = "복원된" 상태
```

## 이벤트 완전성 원칙

### 황금률: "완전한 정보(Self-contained)" 원칙

이벤트는 **외부 데이터를 절대 참조하지 않습니다**.

**3가지 이유**:

1. **이벤트 불변성**: 과거는 바꿀 수 없음
   - "2024년 1월 1일에 100원에 주문했다" = 영원한 사실
   - 현재 가격이 200원이어도, 과거에는 100원이었음

2. **외부 의존성 제거**: 상품 마스터가 변경/삭제되어도 OK
   - 이벤트만으로 상태 복원 가능
   - 외부 테이블이 사라져도 문제없음

3. **시간 여행 가능**: 과거 특정 시점 상태 복원
   - "2024년 1월의 상태"를 복원하려면 당시 가격 필요
   - 외부 참조하면 현재 가격만 얻을 수 있음

### ❌ 잘못된 방식 (외부 참조)

```typescript
// ❌ 나쁜 예: productId만 저장
export class OrderCreatedEvent {
  constructor(
    public readonly orderId: string,
    public readonly productId: string,  // 상품 ID만 저장
  ) {}
}

// ❌ 복원 시 문제 발생
onOrderCreatedEvent(event: OrderCreatedEvent) {
  // 상품 마스터에서 현재 가격 조회
  const product = await productRepository.findById(event.productId);
  this.price = product.price;  // ← 현재 가격! (잘못됨!)

  // 문제점:
  // 1. 주문 시점의 가격이 아님 ❌
  // 2. 상품이 삭제되면 복원 불가 ❌
  // 3. 과거 시점 복원 불가능 ❌
}
```

### ✅ 올바른 방식 (완전한 정보)

```typescript
// ✅ 좋은 예: 모든 필요한 정보 저장
export class OrderCreatedEvent {
  constructor(
    public readonly orderId: string,
    public readonly productId: string,
    public readonly productName: string,  // ✅ 이름도 저장
    public readonly price: number,        // ✅ 가격도 저장
    public readonly quantity: number,     // ✅ 수량도 저장
    public readonly discountRate: number, // ✅ 할인율도 저장
  ) {}
}

// ✅ 복원 시 완벽
onOrderCreatedEvent(event: OrderCreatedEvent) {
  this.price = event.price;  // ← 주문 시점의 가격! ✅

  // 장점:
  // 1. 주문 시점의 정확한 가격 ✅
  // 2. 상품 삭제되어도 복원 가능 ✅
  // 3. 과거 시점 정확히 복원 ✅
}
```

## 가격 변경 시나리오

### 질문: 주문 시 100원, 결제 시 200원이면?

**시나리오**:
- 주문 생성 시: A 제품 가격 = 100원
- 결제 시점: A 제품 가격 = 200원 (상품 마스터에서 변경됨)

**질문**: 상태 복원 시 어떤 가격을 사용하나?

**정답**: **주문 생성 시점의 100원을 사용합니다!**

### 타임라인으로 이해하기

```
┌─────────────────────────────────────────────────┐
│ 2024년 1월 1일 - 주문 생성                      │
├─────────────────────────────────────────────────┤
│ 상품 마스터:                                    │
│   A 제품 가격: 100원                            │
│                                                 │
│ CreateOrderCommand 실행:                        │
│   - Controller가 상품 마스터에서 가격 조회      │
│   - price = 100원 (현재 가격)                   │
│                                                 │
│ OrderCreatedEvent 발행:                         │
│   {                                             │
│     orderId: "ORDER-123",                       │
│     productId: "PROD-A",                        │
│     price: 100,          ← ✅ 100원 저장!       │
│     quantity: 1,                                │
│     finalAmount: 100                            │
│   }                                             │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│ 2024년 2월 1일 - 상품 가격 변경                 │
├─────────────────────────────────────────────────┤
│ 상품 마스터:                                    │
│   A 제품 가격: 100원 → 200원 (변경!)            │
│                                                 │
│ Event Store:                                    │
│   OrderCreatedEvent의 price는 여전히 100원! ✅  │
│   (이벤트는 불변!)                              │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│ 2024년 3월 1일 - 상태 복원 (Query)              │
├─────────────────────────────────────────────────┤
│ getOrderById("ORDER-123") 호출:                 │
│                                                 │
│ 1. Event Store에서 이벤트 조회:                 │
│    events = [OrderCreatedEvent { price: 100 }]  │
│                                                 │
│ 2. 빈 Aggregate 생성:                           │
│    order = new OrderAggregate()                 │
│                                                 │
│ 3. 이벤트 재생:                                 │
│    order.onOrderCreatedEvent(event)             │
│    → this.price = event.price    ← ✅ 100원!    │
│    → this.finalAmount = 100      ← ✅ 100원!    │
│                                                 │
│ 4. 복원된 상태:                                 │
│    order.price = 100원 ✅                       │
│    (현재 상품 마스터의 200원이 아님!)           │
└─────────────────────────────────────────────────┘
```

## 코드로 확인하기

### 1️⃣ OrderCreatedEvent - 가격이 이벤트에 포함됨

```typescript
// order-created.event.ts
export class OrderCreatedEvent {
  constructor(
    public readonly orderId: string,
    public readonly userId: string,
    public readonly productId: string,
    public readonly productName: string,
    public readonly quantity: number,
    public readonly price: number,      // ✅ 주문 시점의 가격!
    public readonly discountRate: number,
    public readonly createdAt: Date,
  ) {}

  // 최종 결제 금액 (할인 적용 후)
  get finalAmount(): number {
    return this.price * this.quantity * (1 - this.discountRate / 100);
    //     ↑ 이벤트에 저장된 가격 사용
  }
}
```

### 2️⃣ onOrderCreatedEvent - 이벤트의 가격을 Aggregate에 저장

```typescript
// order.aggregate.ts
onOrderCreatedEvent(event: OrderCreatedEvent) {
  this.orderId = event.orderId;
  this.userId = event.userId;
  this.productId = event.productId;
  this.productName = event.productName;
  this.quantity = event.quantity;
  this.price = event.price;              // ✅ 이벤트의 가격 사용!
  this.discountRate = event.discountRate;
  this.totalAmount = event.totalAmount;  // ✅ 이벤트에서 계산된 금액
  this.finalAmount = event.finalAmount;  // ✅ 이벤트에서 계산된 금액
  this.status = OrderStatus.CREATED;
}
```

### 3️⃣ EventStore - 상태 복원 과정

```typescript
// event-store.service.ts
async getOrderById(orderId: string): Promise<OrderAggregate | null> {
  const events = this.getEventsByOrderId(orderId);

  if (events.length === 0) {
    return null;
  }

  // Aggregate 생성
  const order = new OrderAggregate(orderId);

  // 모든 이벤트를 순서대로 재생하여 상태 복원
  for (const event of events) {
    this.applyEventToAggregate(order, event);
  }

  return order;
}

private applyEventToAggregate(order: OrderAggregate, event: IEvent) {
  if (event instanceof OrderCreatedEvent) {
    order.onOrderCreatedEvent(event);  // ← 이벤트의 price 사용!
  } else if (event instanceof PaymentSucceededEvent) {
    order.onPaymentSucceededEvent(event);
  }
  // ... 다른 이벤트들도 마찬가지
}
```

## 실무에서의 함의

### 1. 비즈니스 정합성

```
고객: "2024년 1월에 100원 주고 주문했는데,
       왜 지금 조회하니 200원이라고 나와요?"

❌ 외부 참조 방식:
   → "죄송합니다. 현재 가격은 200원입니다." (고객 불만!)

✅ 이벤트 소싱:
   → "고객님이 주문하신 시점의 가격은 100원이 맞습니다." (정확!)
```

### 2. 감사 추적 (Audit Trail)

```
세무 감사:
"2024년 1월 거래 내역을 정확히 보여주세요"

❌ 외부 참조:
   → 현재 가격만 알 수 있음 (감사 불가!)

✅ 이벤트 소싱:
   → 당시 가격, 할인율, 모든 정보 정확히 복원 (완벽한 감사 추적!)
```

### 3. 시간 여행 (Time Travel)

```
"2024년 1월 31일 23시 59분의 주문 상태를 보고 싶어요"

❌ 외부 참조:
   → 불가능 (현재 데이터만 조회 가능)

✅ 이벤트 소싱:
   → 해당 시점까지의 이벤트만 재생 (완벽한 시간 여행!)
```

### 4. 데이터 무결성

```
상황: 상품 마스터에서 A 제품이 삭제됨

❌ 외부 참조:
   → 주문 복원 불가능! (상품 정보 없음)
   → 에러 발생: "Product not found"

✅ 이벤트 소싱:
   → 문제없음! (이벤트에 모든 정보 있음)
   → 상품이 삭제되어도 주문 이력 조회 가능
```

## 이벤트 설계 체크리스트

이벤트 설계 시 다음을 확인하세요:

### 필수 항목

- [ ] **주문 금액**: 주문 시점의 가격 포함? ✅
- [ ] **상품 정보**: 상품명, 수량, 단가 모두 포함? ✅
- [ ] **할인 정보**: 할인율, 할인 금액 포함? ✅
- [ ] **시간 정보**: 이벤트 발생 시각 포함? ✅

### 검증 항목

- [ ] **외부 참조 없음**: productId로 조회하지 않아도 되나? ✅
- [ ] **완전성**: 이 이벤트만으로 상태 복원 가능? ✅
- [ ] **불변성**: 이벤트 발행 후 수정 가능성 없나? ✅
- [ ] **명확성**: 이벤트 이름이 과거형이고 의미가 명확한가? ✅

## 비유로 이해하기

### 🎬 영화 vs 사진

**전통적 DB = 사진 (Snapshot)**
```
┌─────────────┐
│ 최종 모습만 │  ← 현재 상태만 저장
│   저장됨    │     어떻게 변했는지 모름
└─────────────┘
```

**이벤트 소싱 = 영화 (Event Log)**
```
┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
│ 장면1│→│ 장면2│→│ 장면3│→│ 장면4│
└──────┘ └──────┘ └──────┘ └──────┘
                              ↓
                         영화 재생
                              ↓
                         최종 모습 복원!
```

### 🏗️ 건축 과정

**전통적 DB = 완성된 건물**
```
┌─────────────┐
│   🏠 건물   │  ← 현재 상태만 저장
│  (완성품)   │
└─────────────┘
```

**이벤트 소싱 = 건축 과정**
```
1. 기초 공사 (OrderCreated)
   ↓
2. 골조 세우기 (PaymentAttempted)
   ↓
3. 내부 인테리어 (PaymentSucceeded)
   ↓
4. 완공 (OrderCompleted)
   ↓
과정을 다시 재생 → 건물 복원!
```

## 핵심 정리

### 상태 복원 (State Reconstruction)

**정의**: 이벤트만 저장하고, 상태는 필요할 때마다 이벤트를 재생하여 만듦

**과정**:
1. 빈 Aggregate 생성
2. 이벤트 순차 재생
3. 최종 상태 계산

**장점**:
- 완벽한 감사 추적
- 시간 여행 가능
- 모든 변경 이력 보존

### 이벤트 완전성 원칙

**정의**: 이벤트는 외부 데이터를 참조하지 않고, 모든 필요한 정보를 포함

**원칙**:
1. **이벤트 불변성**: 과거는 바꿀 수 없음
2. **외부 의존성 제거**: 이벤트만으로 복원 가능
3. **시간 여행 가능**: 과거 시점 정확히 복원

**실천**:
- 가격, 상품명, 수량 등 모든 정보를 이벤트에 저장
- productId로 조회하지 않고 이벤트 데이터 사용
- 이벤트만으로 완전한 상태 복원 가능하도록 설계
