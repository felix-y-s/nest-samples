# Order-Payment 도메인 통합 설계 문서

## 📌 개요

이벤트 소싱 환경에서 Order 도메인과 Payment 도메인 간 상태 공유를 위한 아키텍처 설계 문서입니다.

### 목표
- Order와 Payment 도메인의 명확한 경계 설정
- 이벤트 기반 통신을 통한 느슨한 결합 구현
- 각 도메인의 독립적인 상태 관리 및 복원 가능성 확보

---

## 🔍 현재 구조 분석

### 주요 문제점

1. **도메인 경계 위반**
   - `OrderAggregate`가 Payment 관련 로직(`initiatePayment`, `completePayment`, `failPayment`)을 직접 포함
   - Payment 도메인이 독립적인 Aggregate로 동작하지 못함
   - Order 이벤트가 `/order/events/` 경로에 있고, Payment는 이를 참조하는 구조

2. **상태 동기화 문제**
   - Order와 Payment가 각자의 상태를 가지지만, 명확한 동기화 메커니즘 부재
   - `OrderCreatedHandler`에서 두 가지 방식으로 Payment를 시작하는 중복 로직 존재

3. **이벤트 소유권 불명확**
   - `PaymentAttemptedEvent`가 `/order/events/`에 위치
   - Payment 도메인의 이벤트가 Order 경로에 있어 도메인 경계가 모호함

4. **EventStore의 Aggregate ID 추출 문제** ⚠️
   - `extractAggregateId()`가 `orderId`를 최우선으로 선택
   - Payment 이벤트가 Order의 이벤트 스트림에 저장되는 심각한 오류
   - `aggregateId` 필드가 최하위 우선순위 (4순위)
   - Repository가 명시적으로 aggregateId를 전달할 수 없는 구조

## 🎯 설계 원칙

1. **도메인 독립성**: Order와 Payment는 각각 독립적인 Aggregate로 관리
2. **이벤트 기반 통신**: 도메인 간 상태 공유는 이벤트로만 처리
3. **명확한 소유권**: 각 이벤트는 발행 도메인에서 소유
4. **Read Model 분리**: 상태 조회는 각 도메인의 Read Model을 통해 처리
5. **Aggregate ID 명확화**: 모든 이벤트는 명확한 aggregateId를 가져야 함

## ⚠️ EventStore 문제 및 해결 방안

### 문제 상황

#### **1. extractAggregateId의 잘못된 우선순위**

**현재 코드**:
```typescript
// src/shared/event-store/event-store.service.ts
private extractAggregateId(event: any): string | null {
  if (event.orderId) return event.orderId;      // 1순위 ❌
  if (event.userId) return event.userId;        // 2순위
  if (event.id) return event.id;                // 3순위
  if (event.aggregateId) return event.aggregateId;  // 4순위 ← 가장 낮음!
}
```

**결과**:
```typescript
// Payment 이벤트가 Order의 스트림에 잘못 저장됨!
PaymentStartedEvent {
  paymentId: 'payment-123',     // ← 실제 Aggregate ID
  orderId: 'order-456',         // ← 관계 정보일 뿐인데 이게 선택됨!
  userId: 'user-1',
  amount: 10000,
}

// EventStore 저장 결과
eventStore.set('order-456', [
  OrderCreatedEvent { orderId: 'order-456' },
  PaymentStartedEvent { ... }  // ← Order 스트림에 잘못 저장! ❌
])

// Payment Aggregate 복원 시도
paymentRepo.findById('payment-123')  // → [] 빈 배열! ❌
```

#### **2. orderId는 Aggregate ID가 아닌 관계 정보**

```
┌─────────────────────────────────────────────┐
│ Payment 이벤트의 필드 역할                    │
├─────────────────────────────────────────────┤
│ paymentId    → Aggregate ID (스트림 식별자)  │
│ orderId      → 관계 정보 (어떤 Order와 연결?) │
│ userId       → 관계 정보 (어떤 User와 연결?)  │
│ transactionId → 외부 시스템 ID (PG사)        │
└─────────────────────────────────────────────┘
```

**이벤트 소싱의 황금률**:
> "한 Aggregate의 이벤트는 한 스트림에만 저장된다"
>
> 💡 **상세 설명**: [이벤트 스트림 개념 가이드](./event-stream-concept.md)를 참고하세요.

```
✅ 올바른 구조:
Order Aggregate (order-456):
  → [OrderCreatedEvent, OrderCompletedEvent]

Payment Aggregate (payment-123):
  → [PaymentStartedEvent, PaymentSuccessedEvent]

❌ 현재 구조 (orderId 우선 시):
Order Aggregate (order-456):
  → [OrderCreatedEvent, PaymentStartedEvent ← 잘못!]

Payment Aggregate (payment-123):
  → [] ← 비어있음!
```

### 해결 방안

#### **방안 2: Interface 기반 aggregateId 필드 추가**

**장점**: 명확하고 확장 가능, 타입 강제
**단점**: 기존 이벤트 수정 필요, aggregateId와 도메인 ID(paymentId, orderId) 중복

```typescript
// Base Event Interface
interface DomainEvent extends IEvent {
  readonly aggregateId: string;  // ✅ 모든 이벤트 필수
}

// Payment 이벤트
export class PaymentStartedEvent implements DomainEvent {
  public readonly aggregateId: string,  // ✅ 'payment-123' (스트림 식별자)

    public readonly orderId: string,      // 'order-456' (관계 정보)
    public readonly userId: string,       // 'user-1' (관계 정보)
    public readonly amount: number,
    public readonly startedAt: Date,
  ) {
    this.aggregateId = paymentId;
  }
}

// Order 이벤트
export class OrderCreatedEvent implements DomainEvent {
  public readonly aggregateId: string,  // ✅ 'order-456' (스트림 식별자)
  constructor(
    public readonly orderId: string,      // 'order-456' (도메인 ID)
    public readonly userId: string,       // 'user-1' (관계 정보)
    // ...
  ) {
    this.aggregateId = orderId;
  }
}
```

**extractAggregateId 단순화**:
```typescript
private extractAggregateId(event: any): string | null {
  // ✅ aggregateId만 확인 (명확하고 단순)
  if (event.aggregateId && typeof event.aggregateId === 'string') {
    return event.aggregateId;
  }

  // Fallback (하위 호환성, 점진적 마이그레이션)
  console.warn(`[EventStore] aggregateId 없음: ${event.constructor.name}`);

  if (event.paymentId) return event.paymentId;
  if (event.orderId) return event.orderId;

  return null;
}
```

#### **방안 3: BaseEvent 추상 클래스 사용 (⭐ 추천)**

**장점**:
- 현재 자동 저장 메커니즘 유지 (EventBus 구독)
- Repository 코드 변경 불필요
- aggregateId 명확하게 지정
- 타입 안전성 확보

**단점**: 기존 이벤트 수정 필요 (모든 이벤트가 BaseEvent 상속)

**1. BaseEvent 추상 클래스 생성**:

**4. EventStore는 현재 구조 유지**:
```typescript
@Injectable()
export class EventStoreService {
  private readonly eventStore = new Map<string, IEvent[]>();

  constructor(private readonly eventBus: EventBus) {}

  // ❌ 자동 저장(구독) 제거 (명시적 저장 사용)
  // onModuleInit() {
  //   this.eventBus.subscribe((event: IEvent) => {
  //     this.saveEvent(event);
  //   });
  // }

  /**
   * ✅ 명시적 이벤트 저장 (Repository에서 호출)

  async saveEvents(aggregateId: string, events: IEvent[]): Promise<void> {
    // 💡 EventStoreService의 역할: "DB 어댑터"

    const newEvents = [...existingEvents, ...events];
    this.eventStore.set(aggregateId, newEvents);

    // ⭐️ 미래: MongoDB 도입 시 여기만 바꾸면 됨 (Repository 수정 불필요)

  }

```

**5. Repository는 기존 코드 그대로 유지**:
```typescript
@Injectable()
export class PaymentRepository {
  constructor(private readonly eventStore: EventStoreService) {}

  async save(payment: PaymentAggregate): Promise<void> {
    const events = payment.getUncommittedEvents();
    if (events.length === 0) return;

    // 1. DB에 먼저 저장 (Explicit)
    await this.eventStore.saveEvents(payment.getId(), events);

    // 2. 이벤트 발행 (메모리)
    payment.commit(); 
  }

  async findById(paymentId: string): Promise<PaymentAggregate | null> {
    const events = this.eventStore.getEvents(paymentId);
    if (events.length === 0) return null;

    const payment = new PaymentAggregate(paymentId);
    for (const event of events) {
      this.applyEventToAggregate(payment, event);
    }
    return payment;
  }
}
```

**왜 이 방식이 좋은가?**
1. **현재 구조 유지**: EventBus 자동 구독 메커니즘을 그대로 사용
2. **코드 변경 최소화**: Repository 코드 수정 불필요
3. **타입 안전성**: BaseEvent 추상 클래스로 컴파일 타임 체크
4. **명확한 의도**: aggregateId가 명시적으로 선언됨

### 권장 구현 순서

**Phase 0: EventStore 수정 (최우선) - BaseEvent 방식**

1. **BaseEvent 추상 클래스 생성**
   ```typescript
   // src/shared/events/base.event.ts
   export abstract class BaseEvent {
     abstract readonly aggregateId: string;
   }
   ```

2. **extractAggregateId 우선순위 수정**
   ```typescript
   private extractAggregateId(event: any): string | null {
     // aggregateId를 최우선으로
     if (event.aggregateId && typeof event.aggregateId === 'string') {
       return event.aggregateId;
     }
     // Fallback (하위 호환성)
     if (event.paymentId) return event.paymentId;
     if (event.orderId) return event.orderId;
     if (event.userId) return event.userId;
     if (event.id) return event.id;
     return null;
   }
   ```

3. **모든 이벤트가 BaseEvent 상속** (점진적 적용)
   - Payment 이벤트: PaymentStartedEvent, PaymentSuccessedEvent, PaymentFailedEvent
   - Order 이벤트: OrderCreatedEvent, OrderCompletedEvent, OrderCancelledEvent
   - 생성자에서 `this.aggregateId = paymentId` (또는 `orderId`) 설정

4. **Repository는 수정 불필요**
   - 기존 `payment.commit()` 코드 그대로 사용
   - EventBus 자동 저장 메커니즘 활용

**중요**: EventStore 수정 없이는 Order-Payment 통합이 제대로 작동하지 않습니다!
**장점**: 현재 자동 저장 구조를 유지하면서 aggregateId 문제만 해결

## 📊 개선된 아키텍처

### 시스템 구조도

```
┌─────────────────────────────────────────────────────────────┐
│                      EVENT BUS (공유 인프라)                    │
└─────────────────────────────────────────────────────────────┘
         ↑                                    ↑
         │ publish                            │ publish
         │                                    │
┌────────┴──────────┐              ┌─────────┴────────┐
│   Order Domain    │              │  Payment Domain   │
│                   │              │                   │
│ ┌───────────────┐ │              │ ┌───────────────┐ │
│ │Order Aggregate│ │              │ │Payment        │ │
│ │               │ │              │ │Aggregate      │ │
│ │ - orderId     │ │              │ │               │ │
│ │ - status      │ │              │ │ - paymentId   │ │
│ │ - amount      │ │              │ │ - orderId     │ │
│ └───────────────┘ │              │ │ - status      │ │
│                   │              │ │ - amount      │ │
│ Events:           │              │ └───────────────┘ │
│ - OrderCreated    │              │                   │
│ - OrderCompleted  │              │ Events:           │
│ - OrderCancelled  │              │ - PaymentStarted  │
│                   │              │ - PaymentSucceeded│
│                   │              │ - PaymentFailed   │
└───────────────────┘              └───────────────────┘
         │                                    │
         │ subscribe                          │ subscribe
         ↓                                    ↓
┌───────────────────┐              ┌───────────────────┐
│Payment Domain     │              │Order Domain       │
│Event Handlers     │              │Event Handlers     │
│                   │              │                   │
│- OrderCreated     │              │- PaymentSucceeded │
│  → PaymentStarted │              │  → OrderCompleted │
│                   │              │- PaymentFailed    │
│                   │              │  → OrderCancelled │
└───────────────────┘              └───────────────────┘
```

### 이벤트 흐름 시퀀스

```
1. 주문 생성 흐름:
   User → CreateOrderCommand
   → OrderAggregate.createOrder()
   → OrderCreatedEvent 발행
   → Payment Domain의 OrderCreatedHandler가 수신
   → PaymentAggregate.startPayment()
   → PaymentStartedEvent 발행
   → Payment Domain의 PaymentStartedHandler가 수신

2. 결제 성공 흐름:
   Payment Gateway → PaymentAggregate.completePayment()
   → PaymentSucceededEvent 발행
   → Order Domain의 PaymentSucceededHandler가 수신
   → OrderAggregate.completeOrder()
   → OrderCompletedEvent 발행

3. 결제 실패 흐름:
   Payment Gateway → PaymentAggregate.failPayment()
   → PaymentFailedEvent 발행
   → Order Domain의 PaymentFailedHandler가 수신
   → OrderAggregate.cancelOrder()
   → OrderCancelledEvent 발행
```

### 2. Aggregate 책임 분리

#### OrderAggregate 책임

**유지할 메서드**:
- ✅ `createOrder()` - 주문 생성
- ✅ `completeOrder()` - Payment 성공 이벤트 수신 후 주문 완료

**제거할 메서드**:
- ❌ `initiatePayment()` - Payment Aggregate로 이동
- ❌ `completePayment()` - Payment Aggregate로 이동
- ❌ `failPayment()` - Payment Aggregate로 이동

#### PaymentAggregate 책임

**추가/개선할 메서드**:
- ✅ `startPayment()` - Order 생성 이벤트 수신 후 결제 시작
- ✅ `processPayment()` - 결제 처리
- ✅ `completePayment()` - 결제 성공 처리
- ✅ `failPayment()` - 결제 실패 처리

#### 1.2 PaymentAggregate 개선

**개선 내용**:
```typescript
export class PaymentAggregate extends AggregateRoot {
  private paymentId: string;
  private orderId: string;
  private userId: string;
  private amount: number;
  private status: PaymentStatus;
  private transactionId?: string;

  constructor(paymentId: string) {
    super();
    this.paymentId = paymentId;
    this.status = PaymentStatus.PENDING;
  }

  // Order 생성 이벤트 수신 시 호출
  startPayment(orderId: string, userId: string, amount: number) {
    if (this.status !== PaymentStatus.PENDING) {
      throw new Error('결제는 PENDING 상태에서만 시작할 수 있습니다');
    }

    this.apply(
      new PaymentStartedEvent(
        this.paymentId,
        orderId,
        userId,
        amount,
        new Date(),
      ),
    );
  }

  // 외부 결제 게이트웨이 호출
  processPayment() {
    if (this.status !== PaymentStatus.PENDING) {
      throw new Error('결제 처리는 PENDING 상태에서만 가능합니다');
    }

    this.apply(
      new PaymentProcessingEvent(
        this.paymentId,
        this.orderId,
        new Date(),
      ),
    );
  }

  // 결제 게이트웨이로부터 성공 응답 수신
  completePayment(transactionId: string) {
    if (this.status !== PaymentStatus.PROCESSING) {
      throw new Error('결제 완료는 PROCESSING 상태에서만 가능합니다');
    }

    this.apply(
      new PaymentSucceededEvent(
        this.paymentId,
        this.orderId,
        this.userId,
        this.amount,
        transactionId,
        new Date(),
      ),
    );
  }

  // 결제 게이트웨이로부터 실패 응답 수신
  failPayment(reason: string) {
    this.apply(
      new PaymentFailedEvent(
        this.paymentId,
        this.orderId,
        this.userId,
        this.amount,
        reason,
        new Date(),
      ),
    );
  }

  // 이벤트 핸들러
  onPaymentStartedEvent(event: PaymentStartedEvent) {
    // paymentId는 생성자에서 이미 설정됨 (재설정 불필요)
    // 불변 속성은 최초 1회만 설정
    this.orderId = event.orderId;
    this.userId = event.userId;
    this.amount = event.amount;
    this.status = PaymentStatus.PENDING;
  }

  onPaymentProcessingEvent(event: PaymentProcessingEvent) {
    // 상태 변경만 (불변 속성은 재설정 안 함)
    this.status = PaymentStatus.PROCESSING;
  }

  onPaymentSucceededEvent(event: PaymentSucceededEvent) {
    // 성공 관련 속성만 설정
    this.transactionId = event.transactionId;
    this.status = PaymentStatus.SUCCEEDED;
    // orderId, userId, amount는 이미 설정됨 (재설정 안 함)
  }

  onPaymentFailedEvent(event: PaymentFailedEvent) {
    // 실패 관련 속성만 설정
    this.status = PaymentStatus.FAILED;
    // orderId, userId, amount는 이미 설정됨 (재설정 안 함)
  }

  // ✅ 명시적 저장 시 Repository에서 사용
  getUncommittedEvents(): any[] {
    return super.getUncommittedEvents();
  }
}
```

#### 4.1 PaymentRepository 생성 (Command 측면 - Aggregate 복원용)

**목적**: EventStore에서 이벤트를 재생하여 PaymentAggregate를 복원합니다.

```typescript
// apps/event-sourcing-sample/src/payment/repositories/payment.repository.ts
import { Injectable } from '@nestjs/common';
import { EventStoreService } from '@shared/event-store/event-store.service';
import { PaymentAggregate } from '@payment/aggregates/payment.aggregate';
import { IEvent } from '@nestjs/cqrs';
import {
  PaymentStartedEvent,
  PaymentSuccessedEvent,
  PaymentFailedEvent,
} from '@payment/events';

@Injectable()
export class PaymentRepository {
  constructor(private readonly eventStore: EventStoreService) {}

  /**
   * ID로 Payment Aggregate 조회 및 복원
   * EventStore에서 이벤트를 재생하여 Aggregate 상태 복원
   */
  async findById(paymentId: string): Promise<PaymentAggregate | null> {
    const events = this.eventStore.getEvents(paymentId);

    if (events.length === 0) {
      return null;
    }

    // Aggregate 생성
    const payment = new PaymentAggregate(paymentId);

    // 모든 이벤트를 순서대로 재생하여 상태 복원
    for (const event of events) {
      this.applyEventToAggregate(payment, event);
    }

    return payment;
  }

  /**
   * Aggregate에 이벤트 적용 (Replay)
   */
  private applyEventToAggregate(payment: PaymentAggregate, event: IEvent) {
    if (event instanceof PaymentStartedEvent) {
      payment.onPaymentStartedEvent(event);
    } else if (event instanceof PaymentSuccessedEvent) {
      payment.onPaymentSuccessedEvent(event);
    } else if (event instanceof PaymentFailedEvent) {
      payment.onPaymentFailedEvent(event);
    }
  }

  /**
   * Aggregate 저장 (새로운 이벤트 저장)
   */
  async save(payment: PaymentAggregate): Promise<void> {
    const events = payment.getUncommittedEvents();
    if (events.length === 0) return;

    // 1. DB에 먼저 저장 (Explicit)
    this.eventStore.saveEvents(events, payment.getId());

    // 2. 이벤트 발행 (메모리)
    payment.commit();
  }
}
```

#### 4.2 PaymentReadModelRepository 생성 (Query 측면 - 쿼리 최적화용)

**목적**: 이벤트 핸들러가 동기화한 현재 상태를 빠르게 조회합니다.

```typescript
// apps/event-sourcing-sample/src/payment/repositories/payment-read-model.repository.ts
import { Injectable } from '@nestjs/common';

export interface PaymentReadModel {
  paymentId: string;
  orderId: string;
  userId: string;
  amount: number;
  status: string;
  transactionId?: string;
  createdAt: Date;
  updatedAt: Date;
}

@Injectable()
export class PaymentReadModelRepository {
  private payments: Map<string, PaymentReadModel> = new Map();

  async findById(paymentId: string): Promise<PaymentReadModel | null> {
    return this.payments.get(paymentId) || null;
  }

  async findByOrderId(orderId: string): Promise<PaymentReadModel | null> {
    const payments = Array.from(this.payments.values());
    return payments.find(p => p.orderId === orderId) || null;
  }

  /**
   * 이벤트 핸들러가 호출하여 Read Model 동기화
   */
  async sync(payment: Partial<PaymentReadModel>): Promise<void> {
    const existing = this.payments.get(payment.paymentId!);
    if (existing) {
      this.payments.set(payment.paymentId!, {
        ...existing,
        ...payment,
        updatedAt: new Date(),
      });
    } else {
      this.payments.set(payment.paymentId!, payment as PaymentReadModel);
    }
  }
}
```

```
   ├─ initiatePayment() 제거

   ├─ failPayment() 제거
   └─ completeOrder() 추가
   ↓
6단계: 기존 코드 정리
   ├─ /order/events/payment-*.event.ts 제거
   └─ Import 경로 수정
   ↓
7단계: 모듈 의존성 정리
   ├─ PaymentModule providers 정비
   └─ OrderModule providers 정비
   ↓
8단계: Repository 및 Read Model 정비
   ├─ PaymentRepository 생성
   └─ 쿼리 핸들러 추가
   ↓
9단계: 테스트 작성 및 검증
   ├─ 단위 테스트
   └─ 통합 테스트
```

## 💡 핵심 개념

### 이벤트 소싱에서 도메인 간 통신

1. **이벤트는 과거 사실의 기록**
   - "OrderCreated"는 "주문이 생성되었다"는 과거 사실
   - Payment 도메인은 이 사실에 **반응**하여 결제를 시작

2. **각 도메인은 독립적인 상태를 관리**
   - Order는 OrderStatus를 관리
   - Payment는 PaymentStatus를 관리
   - 이벤트를 통해 상태를 동기화

3. **이벤트는 소유 도메인에서 관리**
   - Order 이벤트 → `/order/events/`
   - Payment 이벤트 → `/payment/events/`
   - 명확한 소유권으로 도메인 경계 유지

### 리팩토링 전략

**"확장 후 축소" 전략**:
1. 새로운 구조를 먼저 만들기 (Payment Domain 정비)
2. 기존 코드와 병행 운영
3. 새로운 구조가 안정화되면 기존 코드 제거

**이점**:
- 시스템이 항상 동작하는 상태 유지
- 이벤트 히스토리 손상 방지
- 점진적 마이그레이션 가능

```typescript
async handle(event: PaymentSucceededEvent) {
```

- 실패 시 보상 트랜잭션 실행
- 이벤트 기반으로 상태 관리

## 7. 데이터 영속성 보장 전략 (Explicit Persistence)

이벤트 소싱 아키텍처에서 이벤트를 저장소에 기록하는 방식은 크게 "암시적 저장(Implicit Saving)"과 "명시적 저장(Explicit Saving)"으로 나뉩니다. 본 프로젝트는 데이터 무결성과 트랜잭션 안전성을 위해 **명시적 저장 패턴**을 채택합니다.

### 7.1 암시적 저장 (Implicit Saving) - 현재/지양 ⚠️
- **동작 방식**: Aggregate가 `commit()`을 호출하면 `EventBus`가 이벤트를 발행하고, 백그라운드에서 `EventStoreService`가 이를 구독하여 저장합니다.
- **문제점 (Dual Write)**:
  - 이벤트는 메모리상에서 이미 발행되어 다른 핸들러들이 로직을 수행했지만, DB 저장이 실패할 경우 **데이터 불일치(Inconsistency)**가 발생합니다.
  - "이벤트는 처리되었는데, 기록은 없는" 좀비 트랜잭션 상태가 될 수 있습니다.
  - 저장 시점이 코드상에 명확히 드러나지 않아("Magic"), 흐름을 파악하기 어렵습니다.

### 7.2 명시적 저장 (Explicit Saving) - 제안/표준 ✅
- **동작 방식**: `Repository.save(aggregate)` 메서드를 통해 **먼저 DB에 저장**하고, 저장이 성공한 경우에만 `commit()`으로 이벤트를 발행합니다.
- **장점**:
  1.  **데이터 정합성 보장**: 저장이 실패하면 이벤트 발행도 일어나지 않으므로, 시스템 상태가 언제나 일관되게 유지됩니다.
  2.  **명확한 의도**: 코드를 읽는 사람에게 "여기서 영구적으로 저장된다"는 사실을 명확히 전달합니다.
  3.  **테스트 용이성**: `EventBus` 연결 없이도 Repository 단위 테스트만으로 저장 로직 검증이 가능합니다.

### 7.3 구현 패턴 비교

| 구분 | 암시적 패턴 (Magic) | 명시적 패턴 (Standard) |
|---|---|---|
| **코드** | `payment.commit()` | `await paymentRepo.save(payment)` |
| **순서** | 발행(Publish) → 저장(Save) ❓ | 저장(Save) → 발행(Publish) ✅ |
| **안정성** | 낮음 (저장 실패 시 롤백 불가) | 높음 (저장 성공 시에만 진행) |
| **비고** | 프로토타이핑에 유리 | 실제 운영 환경의 표준 |

따라서 모든 Command Handler는 반드시 `Repository.save()`를 통해 상태를 변경해야 합니다.
